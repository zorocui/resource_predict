## 一、成果概述

本成果是一套面向异构云环境的资源使用预测与调配决策系统，覆盖 **OpenStack 虚拟机** 与 **Kubernetes Workload** 两类资源，打通"指标采集 → 多模型预测 → 证据化误差评估 → 扩缩容决策 → 目标规格生成 → 多重执行门控 → 真实调配执行 → 状态反馈"的完整闭环。

系统以 Python + Flask 实现，前端为无构建依赖的单页应用（原生 JS + 本地化 ECharts），可在纯内网环境离线部署。核心业务包 64 个模块、12,613 行 Python，加入口脚本、测试与基准工具后项目总计 104 个 Python 文件、20,352 行；前端 3,700 行 JavaScript、1,952 行 CSS。配套 390 个自动化测试用例，对外提供 20 个 REST 接口和 6 个功能视图（风险队列、概览、调配任务、数据更新、系统配置、集群配置）。

成果的核心定位不是"再做一个预测模型"，而是把预测结果组织成**可验证的证据链**，并用**分层门控**约束预测结论向真实资源操作转化的全过程，解决预测式弹性伸缩在生产环境中"不敢用、不可查、易振荡"的落地难题。

## 二、现有技术及主要局限

| 现有技术类别 | 代表 | 主要局限 |
| --- | --- | --- |
| 阈值反应式伸缩 | Kubernetes HPA、OpenStack Heat autoscaling、Zabbix/Prometheus 告警触发 | 无预测能力，只能在资源已经紧张后响应；单一阈值无法区分持续趋势与瞬时尖峰 |
| 垂直资源推荐 | Kubernetes VPA | 以历史使用分位数直接推荐 request，缺少未来窗口预测、误差评估与执行门控；不区分扩容与缩容应采用不同基线 |
| 纵横协同伸缩研究 | KOSMOS（ICSOC 2021）、AHPA（AAAI 2023，阿里云 ACK） | 提出纵横协同与预测式伸缩思路，但面向单一容器平台，未覆盖虚拟机；协同结果缺少面向运维的可解释证据与人工复核分流路径 |
| 预测式扩缩容专利 | CN114389953B（基于流量预测的 K8S 动态扩缩容）、CN115774605A（K8S 预测式弹性伸缩） | 以业务流量为预测对象，落到副本数单一维度；未处理容器级 request/limit 双基线、多容器目标映射与跨轮次方向确认 |
| 云管平台容量模块 | 各类 CMP / 运维大屏 | 多为事后统计与静态报表，预测与执行割裂，无误差可追溯性，无自动执行的安全约束 |

归纳起来，现有技术存在五个共性缺口：

1. **预测结论不可追溯**：只输出曲线或推荐值，不输出模型误差、选择依据、数据质量与失败原因，运维无法判断"该不该信"。
2. **利用率口径不一致**：多容器 Workload 中，使用量序列的参与容器范围与 request/limit 的参与容器范围常常不一致，导致利用率失真，进而使目标规格计算偏差。
3. **扩缩容共用单一基线**：Limit 承担运行约束、Request 承担调度预留，二者语义不同，用同一基线判断扩容和缩容会产生方向性错误。
4. **纵向与横向相互放大**：容器规格与副本数各自追求目标利用率时，可能对同一次负载增量重复补偿，形成乘法式容量放大。
5. **抖动防护手段单薄**：普遍依赖单轮预测加固定冷却时间，无法识别"连续多轮同方向"这一稳定性信号，也难以排除短历史、缺失数据和异常点触发的错误调配。

## 三、主要创新点

### 创新点 1：预测证据链——把预测结果组织为可验证的四元对应对象

系统对每个资源的每个指标运行多个候选模型（ARIMA / SARIMA / Prophet / Seasonal Naive / Rolling Mean，以及按误差倒数加权融合的 Ensemble），并把结果组织成 **资源—指标—模型—预测窗口** 四元对应的证据对象，逐条记录：

- 留出窗口误差与滚动回测误差（`rmse`、`mae`、`mape`、`p95_error`、`rolling_rmse`、`rolling_mae`、`rolling_folds`）；
- 复合选型评分来自训练段内部验证：多折时 `selection_rmse = 0.65 × 最近验证折RMSE + 0.35 × 全部验证残差RMSE`，单折时为验证 RMSE；外层独立测试不参与选型；
- 候选模型失败状态与失败原因（`method_failures`）；
- 历史数据覆盖度、数据缺失率与采样间隔；
- 未来窗口预测序列及其均值、峰值、分位值、趋势斜率与持续超限比例。

证据链以 `forecast_error_report.json` 作为**一等输出产物**落盘，与预测结果同批生成，并在 `generate_forecasts.py predict` 模式下对 `raw_index.json` 做 SHA-256 摘要前后校验，确保重算过程未篡改原始数据。后续任何决策都不允许使用脱离证据来源的孤立预测值。

**与现有技术对比**：HPA/VPA 与主流云管平台只暴露推荐结果，不暴露误差与选型依据。本成果使"为什么给出这个建议"可逐层复核，是预测式伸缩从"黑盒推荐"走向"可审计决策"的关键一步。

### 创新点 2：成本感知的模型路由——按序列特征决定是否承担重模型训练成本

面对上万资源、每资源多指标、K8S 还需按容器展开的规模压力，系统不对所有序列统一运行重模型，而是引入两级路由（`pipeline/prophet_routing.py`、`pipeline/model_selection.py`）：

- **重模型准入路由**：依次判定序列长度（有效点 < 48 直接跳过）、近期异常（MAD 鲁棒 z-score > 3.5 优先鲁棒候选）、低方差稳定序列（标准差 < 0.005、极差 < 0.02 或变异系数 < 0.03 跳过），再计算趋势强度与季节强度，仅当 `趋势强度 ≥ 0.18` 或 `季节强度 ≥ 0.25` 时才运行 Prophet；每次跳过都记录结构化原因（`short_series` / `low_variance_stable_series` / `recent_anomaly_prefers_robust_candidate` / `simple_series_covered_by_fast_methods`）。
- **异常鲁棒路由**：检出异常的序列在 `ensemble / seasonal_naive / rolling_mean` 中按 `selection_rmse` 择优，避免参数化模型被离群点带偏。
- **失败降级路由**：被选模型的未来窗口预测不可用时，使用 Rolling Mean 的真实模型名称生成未来序列，并记录原选型与降级原因；不将降级曲线冒充原模型。若兜底同样失败，明确报告失败。

路由模式支持 `auto / always / never` 三档，并强制校验：当不存在任何快速兜底模型时，即使配置为 `never` 也必须运行 Prophet，杜绝"无模型可用"的空转。

**与现有技术对比**：现有预测式伸缩方案通常对全部目标序列套用同一模型，算力开销随资源规模线性膨胀。本成果把模型复杂度作为受控资源进行分配，在保持证据完整的前提下显著降低大规模场景的计算成本。

### 创新点 3：容器级"参与范围一致"的 Request/Limit 双基线利用率序列与非对称判定

K8S 侧从 Prometheus 采集容器 CPU/内存实际使用量，通过 `kube_pod_owner`（必要时经 `kube_replicaset_owner` 回溯）把 Pod 归属解析到 Deployment / StatefulSet / ReplicaSet / DaemonSet 控制器粒度，再按 Workload 与容器名称归并。关键处理是：

```text
cpu_usage_by_limit_workload   = Σ usage(仅累加存在 cpu_limit 的容器)   / Σ cpu_limit
cpu_usage_by_request_workload = Σ usage(仅累加存在 cpu_request 的容器) / Σ cpu_request
```

即分子与分母严格取同一参与容器集合，形成两条**范围一致的双基线利用率序列**（实现见 `providers/k8s_prometheus.py` 的 `_sum_series_by_workload(..., include_keys=...)`）。在此之上采用**非对称判定**：

- 扩容信号基于 **Limit 利用率**（P95 ≥ 0.8 或峰值 ≥ 0.9），因为 Limit 是运行期真实约束；无 Limit 时不提出扩容建议；
- 缩容信号基于 **Request 利用率**（均值 < 0.2 且 P95 < 0.35），因为 Request 决定调度预留与资源浪费；
- 缩容额外引入上升趋势保护，防止在负载爬升初期过早回收资源。

当前资源规格只保存在 `spec.containers.<container>` 容器粒度，不设 Workload 级累加字段，前端亦按容器展示，从数据结构上杜绝口径混用。

**与现有技术对比**：VPA 与多数预测式伸缩专利使用单一基线（通常只有 request 或只有使用率分位数），在多容器（含 sidecar）场景会产生系统性利用率偏差，且无法区分"资源不足"与"资源冗余"两类不同性质的问题。

### 创新点 4：纵向规格与横向副本的总容量协调，以及小规格粒度保护

容器纵向资源目标在 **容器粒度** 计算，副本横向目标在 **Workload 粒度** 计算，两者独立求解后再通过总容量协调规则校验（`core/k8s_workload_decision.py` 的 `_coordinate_total_capacity()`）：

- 以 `单副本资源量 × 副本数` 构造总容量，计算变化比例；
- 缩容方向单轮总容量降幅超过 60% 时，标注"建议分阶段实施"；
- 扩容方向总容量增幅超过 100% 时，标注"请复核是否在预算范围内"；
- per-replica 目标与副本数独立计算，避免同一负载增量被纵横两种方式重复补偿。

同时设置**小规格粒度保护**：目标 request/limit 低于 `2C / 2Gi` 的 Workload 保留毫核与 MiB 级小数粒度，不做偶数对齐，避免 `0.5C` 级别的轻量容器被整数规格对齐放大到 `2C`（4 倍虚增）。VM 侧则相反，CPU 核数按偶数对齐以贴近常见云主机规格，磁盘缩容最小 50GB、且磁盘目标低于当前容量时不进入自动缩容（磁盘使用具有单调性且不可弹性回收）。

多容器 Workload 的目标写入 `target_spec.containers.<container>`，副本数保留在 `target_spec.replicas`；DaemonSet 跳过副本缩放并给出明确警告。

**与现有技术对比**：KOSMOS 等纵横协同方案在控制器层面协调，但缺少对"规格对齐放大"和"总容量变化幅度"的显式约束，也缺少把 Workload 级汇总建议安全映射到具体容器指令的机制。

### 创新点 5：以"动作方向"而非"目标数值"为对象的跨轮次连续确认状态账本

系统把每轮建议归一化为扩容 / 缩容 / 无动作三种**方向**，并在 `outputs/<scope>/action_gate_state.json` 中按资源持久化同方向的连续轮次（保留 30 天）：

- 目标规格数值变化但方向不变时，计数**继续累计**（不因推荐值微调而丢失已确认的稳定性证据）；
- 方向反转、变为保持或数据不足时，计数**重新计数或清零**；
- 扩容默认需连续 2 轮、缩容默认需连续 3 轮；conservative 层级缩容 +1 轮、扩容可 -1 轮，aggressive 层级缩容 -1 轮；
- 状态账本与预测产物同 scope 隔离存放，读写经独立锁保护。

**与现有技术对比**：现有方案普遍以"单轮预测 + 固定冷却时间"抑制抖动。冷却时间只能限制执行频率，无法判断信号是否持续稳定；以目标数值为确认对象的机制又会因推荐值小幅波动而反复重置。以方向为确认对象的跨轮次账本，是对"趋势稳定性"这一维度的显式建模。

### 创新点 6：置信度 × 紧急度双维度协同分流 + 六道执行门控

**置信度**回答"这个建议可信吗"，**紧急度**回答"不处理的话风险多快、多严重地发生"，两者分别计算并协同分流：

```text
置信度 = 最高指标得分 × 0.65 + 平均指标得分 × 0.35 + 多指标加成
       - 混合信号扣分 - 数据质量扣分 - 阻断项扣分 + 执行就绪加成
       （历史覆盖不足 5 天时，非 hold 建议封顶到执行阈值以下）
分级：score ≥ 72 为 high，45 ≤ score < 72 为 medium，其余为 low
```

单项指标得分对 P95 超阈值、峰值超阈值、均值超阈值、持续高/低负载、趋势方向、峰谷差稳定性等信号做归一化加权，并对"只有尖峰而 P95 不强"的情形施加最高 18 分的尖峰惩罚。数据质量与历史覆盖只在一个计算层级参与，避免重复计权；资源级置信度只聚合实际触发调配且与总体动作同向的指标。

紧急度采用**动作相关**设计：扩容计算服务风险紧急度（预测超限幅度、连续超限时长、距首次超限剩余时间、业务保障等级），缩容计算资源浪费紧急度（持续空闲程度、空闲持续时长、配额压力、成本或策略等级），无调配动作时紧急度为零。系统不使用同一个"风险"概念同时描述服务过载与普通低利用率。

```text
紧急度 = 基础动作分 + 置信度加成 + 风险分贡献 + 最强指标贡献
       + 其他指标贡献(0.25×) + 多指标加成 + 混合信号加成 + 目标变化分
       + 仅分析折扣/封顶
```

两者组合形成四条处理路径：高置信高紧急进入高优先级执行候选；低置信高紧急进入紧急人工复核且不自动执行；高置信低紧急进入延迟执行、试运行或合并调配；低置信低紧急保持当前规格继续采样。

高优先级候选仍须通过**六道执行门控**才能创建执行任务：

1. `action_gate = ready`（方向连续确认轮次已满足）；
2. `confidence = high` 且分数达到策略阈值；
3. `data_quality` 达到策略阈值（poor 质量自动跳过执行建议）；
4. 对应动作的 `cooldown` 已结束（扩容 60 分钟、缩容 360 分钟）；
5. `policy_tier` 允许自动执行；
6. 目标规格合法且平台当前能够执行。

门控对不同来源的目标做差异化处理：人工复核确认的目标（`target_source=confirmed`）只能跳过方向轮次检查，数据质量、冷却期与策略检查仍然生效；完全手工指定的 `target_spec` 不要求建议侧的 `action_gate` 与 `confidence`，但仍受策略层级、数据质量、冷却期和 K8S 目标策略校验约束。紧急度只用于排序与分流，**不得单独触发自动执行**。

### 创新点 7：内容寻址不可变分片 + O(1) 索引 + 原子提交的规模化存储架构

面向"数千至数万资源、K8S 容器级指标成倍放大预测负载"的设计基线，系统重构了数据与产物的存储读取路径：

- **内容寻址分片**：原始数据按资源切分为 `raw/<SHA-256(resource_id)前2位>/<resource-hash>-<content-hash>.json`，文件名不含资源 ID，规避非法字符、路径长度与碰撞问题；分片不可变，未变化的资源不重写。
- **O(1) 索引**：`raw_index.json` 只保存全局元数据与 `resource_id → 分片引用` 映射，资源定位由线性扫描改为字典查找；热点资源使用按条目数限制的 LRU 缓存（默认 100 条）。
- **原子提交**：每个分片以临时文件加 `os.replace` 原子落盘，全部分片成功后才原子替换索引；提交失败时读取端继续看到上一份完整快照，绝不出现半份数据。不再被引用的分片保留 300 秒宽限期后由后续提交清理，允许并发请求完成已持有旧索引引用的读取。
- **双 scope 物理隔离**：VM 与 K8S 产物分别写入 `outputs/vm/` 与 `outputs/k8s/`，各自拥有独立索引、分片与门控状态，由 `scoped_out_dir()` / `split_items_by_scope()` 强制分离，`ForecastStore` 在 API 层透明合并，互不覆盖。
- **分级加载**：详情元数据与图表数据解耦，`include_charts=false` 只取元数据，图表按 `metric` / `container` / `history_points` 异步分段加载，默认返回最近 1000 个训练历史点并完整保留测试窗口与未来预测，上限 10000 点、超限返回 400，不提供无边界超大响应。
- **序列级独立保留**：VM、Workload 汇总及 `container_metrics` 的每条序列都独立保留从自身最新样本向前 30 天的窗口，离线资源保留最后已知的有界窗口，避免全局统一裁剪丢失慢变资源的历史。

### 创新点 8：缺口安全的采集与预测边界——不产生"看起来正常"的假预测

Prometheus 采集链路在多个环节做了韧性设计：

- **分片重试**：range 查询按 24 小时分片，每片独立对连接失败、超时、HTTP 429 与 5xx 执行最多 3 次指数退避重试，分片按完整标签集合与时间戳合并；
- **集群级原子性**：任一必需查询或分片最终失败时，该集群本轮不提交部分时间范围，其他成功集群照常更新；多集群混合结果记为 `partial_success`，全部失败记为 `failed`，部分失败不丢弃成功集群的数据；
- **无删除语义的 upsert**：只触及本轮成功返回的 `resource_id`，失败集群或本轮未出现的 Workload 保留既有历史与预测产物，不把"本轮没采到"误判为"资源已下线"；
- **调度周期锚定开始时刻**：增量回看窗口固定为 `调度周期 + overlap`（默认 6 小时 + 1 小时），且以本轮**开始**时刻而非完成时刻计时，使实际间隔为 `max(周期, 拉取耗时)`，默认配置下即使单轮拉取耗时达 420 分钟也不会漏数据；配置保存通过事件立即唤醒调度线程重读开关与周期，且不会重置或提前既有周期；
- **归属查询降级重拉**：`kube_pod_owner` 是只回看约 5 分钟的瞬时查询，与数小时的 range 查询可用性并不同步；查询成功却聚合不出任何 Workload 时，按 15 秒、30 秒退避整轮重拉该集群最多 3 次，错误消息定位到具体断点（容器使用率序列为空 / owner 查询无结果或异常 / owner 标签不匹配 / CPU 与内存序列无法配对）及各序列计数，避免把 kube-state-metrics 重启或查询限流误记为集群配置问题；
- **保守插值**：只插值不超过 3 个采样步的完整短缺口，大缺口保持稀疏，不做长距离伪造；
- **可用性驱动的预测跳过**：以配置 `step_seconds` 为权威采样间隔，从每个指标**最近的连续数据段**评估可用性；连续段不足测试窗口时跳过重算、记录 `prediction_skips` 并保留旧产物；
- **规范未来时间轴**：模型未来值统一重建为从真实测试终点 `test_end_ms + sample_interval_seconds` 开始的规范索引，杜绝不同模型因训练窗口差异产生错位曲线；
- **前端防御性边界**：只绘制严格晚于 `test_end_ms` 的未来点，预测色带覆盖全部可见模型的有效未来时间并集，首尾缺失收缩边界、中间缺失不拆段、有效未来点不足两个时不显示色带；历史线与测试线在大缺口处插入空点并保持 `connectNulls=false`，不跨越采集中断直接连线；`null`、空串与非有限数统一视为缺失，而真实数值 `0` 完整保留。

### 创新点 9：异构资源统一决策框架下的类型适配

VM 与 K8S Workload 共用证据链、置信度、紧急度、门控与执行反馈框架，但决策细节各自适配：

- **VM**：扩容判断综合 P95/峰值超阈值、峰谷差、上升趋势斜率与窗口均值变化；缩容判断受 `max_reduction_ratio`（默认最多缩到当前一半）与最小规格下限（2 核 / 4GB / 50GB）双重保护；目标规格按 CPU、内存、磁盘维度独立计算，超出 100% 时线性推算容量；磁盘扩容阈值比通用阈值低 0.05；
- **Rightsize 检测**：均值 < 0.35 且 P95 < 0.55 的资源标记为过度配置候选，识别"可优化但非极端空闲"的中间地带，这是简单的"低利用率告警"无法覆盖的；
- **策略分级与命名空间感知**：conservative / balanced / aggressive 三级策略差异化阈值与确认轮次，并自动从 spec 识别 namespace（prod / production / payments / core / platform 归为保守组，dev / test / staging / batch 归为激进组），同一集群内不同业务域适用不同伸缩激进度；
- **风险画像**：每资源生成 `risk_profile`，含饱和风险分、空闲机会分、综合风险分、当前生效阈值与冷却时间；
- **Baseline 缺失降级**：K8S 缺少 request/limit 时降级为 trend-only 分析，只出趋势判断不出可执行目标；多容器缺少容器级预测时禁止生成汇总规格指令。

### 创新点 10：从建议到真实执行的闭环与安全约束

- **VM 执行链**：SSH 登录控制节点 → `openstack flavor list` 自动发现可用规格 → 选择或在 `allow_create_flavor=true` 时自动创建目标 flavor → `openstack server resize` → 按 `auto_confirm_resize` 决定自动或人工 `resize --confirm`；
- **K8S 执行链**：`kubectl set resources` 按容器粒度设置 request/limit → 控制器支持时 `kubectl scale` 调整副本数；
- **dry_run / execute 分离**：`dry_run` 只返回计划与预检信息，`execute` 才真正入队，且入队前必须通过 `_execution_gate_failures()` 全量校验；
- **命令注入防护**：所有用户可控值统一经 `shlex.quote()` 转义，凭据类配置文件（`clusters.json`、`k8s_prometheus_clusters.json`）由 `.gitignore` 排除且不进入部署包；
- **成功才写快照**：调配成功后才回写 `summary_index.json` / `details/*.json` / 目标资源 raw 分片 / `raw_index.json` / `manifest.json` 中的规格；命令失败不更新"成功规格"快照，避免产物与真实环境状态背离；
- **反馈闭环**：执行结果、实际命令、执行前后规格与失败原因记入任务记录，并更新冷却期与连续确认状态，后续预测与门控必须读取该反馈，不会忽略刚发生的调配动作。

## 四、先进性：技术指标

### 4.1 大规模详情读取性能（实测）

使用项目自带基准 `benchmarks/resource_detail_benchmark.py`，在 AMD Ryzen 5 5600H（6 核 12 线程）/ 14GB 内存 / Windows 11 工作站上实测。每资源 3 个指标、每指标 2016 个数据点（对应 5 分钟粒度 7 天历史），构建全部内容寻址分片与预测产物后随机抽样读取：

| 资源规模 | 序列总量 | 元数据读取 P50 | 元数据读取 P95 | 图表读取 P50 | 图表读取 P95 | 全流程耗时 |
| --- | --- | --- | --- | --- | --- | --- |
| 500 | 1,500 | 0.25 ms | 2.03 ms | 7.49 ms | 8.65 ms | 4.2 s |
| 5,000 | 15,000 | 1.17 ms | 2.23 ms | 7.48 ms | 8.60 ms | 23.2 s |
| 20,000 | 60,000 | 1.20 ms | 2.41 ms | 7.90 ms | 10.08 ms | 102.5 s |

**资源规模扩大 40 倍（500 → 20,000），单资源详情读取 P95 延迟仅从 2.03 ms 增至 2.41 ms（元数据）、8.65 ms 增至 10.08 ms（图表），基本持平**，实测验证了 O(1) 索引与分片读取的架构设计目标。相对基准内置的验收阈值（元数据 200 ms、图表 500 ms），实测分别留有约 83 倍与 50 倍余量。图表响应恒定裁剪至 1000 个训练历史点（`max_training_points = 1000`），测试窗口与未来预测完整保留，响应体不随历史长度膨胀。

## 五、先进性：功能实现

### 5.1 采集与接入的多模式统一

四种数据接入模式共享同一排他锁与同一"读取目标 raw → 合并 → 写入变化分片 → 原子替换索引 → 部分重预测"序列：

- **Pull 增量**：`POST /api/update-trigger` 调用可插拔的 `IncrementalProvider`，通过 `incremental_provider_path`（`module:function` 格式）指定自定义数据源，无需改动核心代码即可对接既有监控系统；
- **Push 增量**：`POST /api/update-data`（仅更新已有）与 `POST /api/upsert-data`（更新或新增），支持秒 / 毫秒 / ISO 字符串混合时间戳，按 `duplicated(keep="last")` 去重；
- **K8S Prometheus Pull**：页面按钮、API 或 CLI 三种触发方式，多集群并发拉取，支持 Bearer Token 与 Basic Auth 双认证、按集群覆盖命名空间正则；
- **后台定时调度**：`python app.py` 启动后按配置周期自动拉取，配置保存即时生效无需重启。

合并后仅对真正发生变化的资源调用 `generate_predictions_only(resource_ids=...)` 做**部分重预测**，而非全量管线重跑。

### 5.2 运维工作台的可用性设计

- **风险队列**：以紧急度分默认排序，运维打开系统即看到"最该先处理什么"，而非按资源名字典序浏览；
- **公式级可解释**：详情抽屉中的置信度与紧急度均以中文公式串逐项展示分数组成，例如
  `紧急度150 = 基础动作分35 + 置信度加成6 + 风险分贡献12.4 + 最强指标贡献72.1 + 其他指标贡献8.5 + 多指标加成4 + 目标变化分12`
  `置信度76.4 = 最高指标贡献48.1 + 平均指标贡献24.3 + 多指标加成4`
  运维可直接核对每个分数的来源，而不是面对一个无法质疑的数字；
- **容器级多曲线同图**：`container_charts.<container>.<metric>` 使同一 Workload 的多个容器曲线绘制在同一 ECharts 图中，便于定位是哪个容器造成压力；
- **统计口径显式区分**：指标胶囊展示完整历史观测窗口的 Workload 聚合 P95，百分比按参与容器使用量总和除以对应 Request/Limit 总和计算并显示参与容器数（而非容器使用率的算术平均）；详情抽屉统计则标注为当前选中 Container 的范围，两者通过标签与提示明确区分，避免口径混淆；
- **预测区域视觉边界**：橙色预测色带严格从最后一个测试点开始、到最后一个有效未来点结束，与当前时间无关，历史与预测在视觉上不可混淆；
- **页面化配置**：采集、预测、决策三组运行参数与集群凭据全部通过页面读写，保存即校验、失败即回滚，无需登录服务器改文件；
- **数据更新可观测**：更新状态板实时展示运行状态、阶段、数据源、窗口与起止时间，更新历史页展示最近 100 条结果，K8S 多集群拉取按集群分别记录成功/失败、Workload 数、耗时与错误。

### 5.3 产物健康检查与可运维性

`check_outputs.py` 提供产物健康检查，支持 `--json` 机器可读输出与 `--allow-missing-type`（容忍仅有 VM 或仅有 K8S 产物），可用于部署验收与巡检脚本。`ingest_k8s_workloads.py --diagnose --json` 提供独立的连通性诊断，把"集群配置问题"与"临时故障"区分开。

## 六、应用场景

### 场景 1：私有云 / 行业云的资源规格治理

针对 OpenStack 虚拟机存量规模大、规格长期只增不减的现状，系统以 Rightsize 检测识别过度配置候选，以缩容保护与分阶段提示控制回收风险，以 3 轮方向确认与 6 小时冷却避免误缩。适用于金融、政务、能源等对变更安全性要求高、需要人工复核环节的私有云环境。

### 场景 2：Kubernetes 生产集群的 request/limit 精细化调优

容器 request/limit 长期"拍脑袋设置、上线后不再调整"是普遍现象，直接导致节点装箱率低下与调度浪费。系统按容器粒度、按 Request 与 Limit 双基线分别给出目标值，并协调副本数变化，生成可直接执行的 `kubectl` 命令。适用于中大型 K8S 集群的周期性资源治理与成本优化。

### 场景 3：多业务域差异化保障

命名空间感知的策略分级使生产核心域（prod / payments / core）自动适用保守阈值与更多确认轮次，开发测试域（dev / test / staging / batch）适用激进阈值以更快回收资源。适用于同一集群承载多业务域、需要差异化 SLA 与成本考核的组织。

### 场景 4：多集群统一纳管

VM 集群与多个 K8S 集群的 Prometheus 可在同一系统内配置与调度，产物按 scope 物理隔离、API 层透明合并，多集群拉取支持部分成功语义。适用于集团型组织跨数据中心、跨集群的统一资源视图与调配。

### 场景 5：纯内网离线环境

一键打包生成不含凭据的白名单 ZIP，前端 ECharts 本地化，运行期不依赖任何外部网络服务；集群地址与账号由部署人员在页面填写。适用于无法访问公网的内网生产环境，包括涉密与隔离网络。

### 场景 6：预测式运维的能力底座

系统对外提供 20 个 REST 接口，预测证据、置信度、紧急度、目标规格与门控状态均可被上游 ITSM、成本分析或容量规划系统消费，可作为 AIOps 体系的资源预测能力底座，而非孤立的展示工具。

## 九、结论

本成果的先进性不在于使用某一个更优的预测算法，而在于围绕"预测结论如何安全地变成真实资源操作"这一生产落地难题，建立了一套完整的技术体系：以**预测证据链**让结论可追溯，以**成本感知路由**让规模可承受，以**双基线一致性口径**让利用率不失真，以**纵横总容量协调**让控制不互相放大，以**方向连续确认与六道门控**让执行不抖动，以**内容寻址分片与缺口安全边界**让数据在万级规模和真实采集故障下依然可信。

与阈值反应式伸缩、垂直资源推荐及现有预测式伸缩方案相比，本成果在误差可追溯性、利用率口径一致性、扩缩容判定基线区分、纵横容量协调、抖动抑制机制、执行安全门控、异构资源覆盖、真实执行闭环、规模化读取性能与内网离线部署十个维度上均有实质性提升，且所有关键指标均可在本仓库内复现验证。
