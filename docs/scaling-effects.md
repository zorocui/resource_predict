# 调配成效统计与佐证材料

“调配成效”页面统计本系统真实 execute 任务的实测前后变化，支持筛选、详情曲线、CSV、证据 JSON 和浏览器打印。预检（dry_run）不会成为调配成效；旧任务不补造前后证据。页面默认查看缩容，扩容和混合调整分别查看。

## 使用流程

1. 按原流程执行调配。首条远程命令之前，系统冻结任务ID、资源ID、调配前规格、实际目标规格和可用基线证据；原有执行门控不变。
2. 命令成功（VM人工确认完成后）转为“等待实测生效”。本地成功快照不是生效证明，必须有后续真实监控。
3. K8S必须同时匹配目标副本数、每个容器的request/limit规格，并找到同期真实容量达到目标的采样点；VM匹配目标CPU/内存/磁盘规格，统计CPU与内存。首次匹配采样时间是保守的首次观测生效时间，不是精确平台变更时刻。
4. 默认调配前24小时、实测生效后稳定1小时、随后24小时观察窗口。前后有效覆盖率均达到80%，且所有应评估的聚合指标满足条件，才进入“已评估”。默认最大连续采样间隔15分钟；超过该间隔整段不计，不跨长缺口填零或外推尾点。
5. 打开“调配成效”，按方向、资源类型、状态、资源/任务ID和调配开始时间范围筛选。CSV覆盖完整筛选范围，不限当前页；详情可下载该事件的证据JSON或打印当前页面报告。

当前窗口政策是代码级默认值，版本1会随事件冻结，页面不能修改既有事件的观察口径。每个事件从开始算起，在“稳定期+后窗口+7天补齐期”后停止接收迟到证据，显示补齐到期；不是无限等待。

## 指标口径

对同一资源/容器、同一指标和同一分母，在有效采样相邻点之间使用左连续值按时间积分：

```text
平均使用量 = Σ(真实使用量 × 有效时长) / Σ有效时长
平均配置容量 = Σ(同期真实容量 × 有效时长) / Σ有效时长
窗口利用率 = Σ(真实使用量 × 有效时长) / Σ(同期真实容量 × 有效时长) × 100%
覆盖率 = 有效时长 / 完整窗口时长

百分点变化 = 后利用率 - 前利用率
相对变化率 = (后利用率 - 前利用率) / 前利用率 × 100%
配置容量差 = 前平均容量 - 后平均容量
容量回收率 = 配置容量差 / 前平均容量 × 100%
容量差×小时 = 配置容量差 × 后窗口有效小时数
```

P95按有效时长加权。超过100%分母的有效时长另行展示；对Request而言超过100%不等于故障或CPU限流。零基线的相对变化率为null，页面显示破折号；零值本身仍正常显示。负向变化与扩容增加的容量差保留负数，不能筛掉下降样本。

仅作演算：使用1核、配置4核时利用率25%；使用仍为1核、配置缩到2核后利用率50%，增加25个百分点、相对提升100%、容量差2核。这不是本系统的生产实测结论。

汇总按 `资源类型 + 调配方向 + CPU/内存 + 分母` 分组，只纳入已完整评估事件的Workload/VM聚合指标：

- **平均相对变化率**：各有效事件相对变化率的算术平均；零基线事件不进入该分母，同时显示有效数量。
- **前后加权平均利用率**：均使用每个事件的调配前平均容量作为同一组固定权重；再计算加权相对变化率。
- **样本数量**：按调配事件计数，另显示去重资源数；同一资源多次调配分别计入，不宣称是每个资源只出现一次的平均值。
- **容量差及容量差×小时**：累计当前筛选范围内事件的有符号差值，不代表当前集群空闲容量、物理节点回收或金额节省。只看缩容时不包含扩容消耗，不能据此声称全局净节省。

CPU单位是cores、内存单位是GiB，两者不相加。VM以配置容量为分母；K8S分别展示Request/Limit，容器先独立计算，然后要求完整、同期容器成员齐全才汇总Workload。K8S结果不等于物理集群利用率。

## 数据来源与证据契约

K8S采集器新增最多4个历史容量范围查询（CPU/内存×request/limit），复用本轮CPU使用量的rate_window。对每个采样时点，使用量和容量必须来自同一组可观测容器实例；缺失、无效数值保留null。不会用当前request/limit乘历史利用率还原“真实”容量。

采集器目前使用当前owner映射识别Workload。已离开或被重新归属的实例历史可能不完整；此限制随证据导出。调配前已经留档的有效基线不会被调配后“当前成员”重建的历史覆盖；未曾留档且无法匹配旧容量的历史只算缺失，不能伪装成容量漂移或补成完整基线。

VM/自定义数据源需要显式提供同一契约。仓库没有真实VM监控Provider，mock和预测序列不会被认可为实测；仅有旧VM利用率曲线时会保持待评估/到期，直到接入真实的同期使用量与容量。

外部采集结果可携带以下独立字段，由数据导入、raw往返和增量合并保留。所有时间为整数epoch毫秒，usage/capacity必须是同一时点真实监控值。`spec`必须是实际观测规格，不能来自本地建议快照。下面仅为字段示例：

```json
{
  "scaling_evidence": {
    "schema_version": 1,
    "source": "internal_vm_monitor_unfilled",
    "collected_at_ms": 1800000300000,
    "spec": {"cpu_cores": 4, "memory_gb": 8, "disk_gb": 100},
    "sample_interval_ms": 300000,
    "series": [{
      "container": "",
      "metric": "cpu",
      "basis": "capacity",
      "unit": "cores",
      "timestamps": [1800000000000, 1800000300000],
      "usage": [1.0, 1.1],
      "capacity": [4.0, 4.0]
    }]
  }
}
```

K8S每个series的container为容器名、basis为request或limit，usage/capacity是该容器名下同期副本总量。内存metric为memory、unit为GiB。历史容量为0或缺失时不能计算对应利用率。

## 状态和排除原因

| 状态 | 含义 |
| --- | --- |
| executing | 真实任务执行中 |
| awaiting_effective | 命令完成，尚未监控确认目标规格及同期容量 |
| observing | 已确认生效，观察窗口尚未结束 |
| insufficient_data | 窗口结束但覆盖率或所需指标不完整，补齐期内继续接收证据 |
| evaluated | 所需指标完整评估，结果已冻结 |
| failed | 执行失败，不计成效 |
| interrupted | 新的真实调配在前一次观察窗口结束前发生 |
| basis_changed | 有效窗口内还有额外容量变化，不能归于本次调配 |
| evidence_conflict | 同一时点收到冲突的有效观测，不静默覆盖 |
| capture_failed | 证据采集或解析失败，执行事件仍留档 |
| expired | 超过补齐期限，保留已有记录但停止等待 |

窗口已经结束、仅等待迟到数据的事件，不会因为后续调配而被错误标记为截断。全部CPU达标但内存尚不完整时也不会提前冻结事件。未完成、失败或被排除的事件保留在统计分母说明和明细中。

## 存储、导出与审计

每个资源类型输出目录新增 `scaling_effects.sqlite3`，独立于只保留最近1000条的任务JSON，也独立于7天预测留档。仅给真实调配事件保存相关窗口内样本，不另外复制所有未调配资源的历史到成效数据库。已评估结果和证据不会被raw滚动清理改写；该账本没有自动删除历史事件的规则，运维应定期备份并规划存储。

SQLite按资源、事件和时间索引；页面摘要使用缓存聚合表在SQL中统计，分页只解析所选页的事件，不读取所有raw或所有历史事件的完整样本。证据更新沿现有raw提交增量触发，不启动新的轮询线程。证据采集失败不撤销已经成功的远程调配，但会记录日志和任务 `outcome_capture_error`。

JSON包包含冻结前后规格、政策、事件时间、真实series、样本来源ID、采集来源与限制、以及首次确认生效的独立采样证明。顶层SHA256验证整个导出内容：去掉顶层sha256后，用UTF-8、按键排序、紧凑分隔符、不允许NaN的JSON重新计算。SHA256只能检查内容一致性，不是第三方真实性签名；来源batch_id是内部关联ID，不是独立可复算的完整批次哈希。

CSV与页面使用同一筛选和公式，区分空值/零值/负数，字符串首字符的电子表格公式注入会被转义。打印材料建议保留样本数、覆盖率、窗口、生效时间、政策版本和数据来源；不要只截取提升率数字。

前后变化属于观察性证据，业务增长、业务下降、部署变化都可能影响结果。当前不采集请求量、错误率、延迟、OOM或限流，不能声称已验证SLO不下降或证明调配导致全部提升。
